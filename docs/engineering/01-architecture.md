## 1. 部署形态和运行链路

一个所有者、一台常在线的执行主机、一个控制服务、一个 Runner。桌面和手机浏览器经同一私网 HTTPS 地址访问。控制服务可独立重启。Runner 负责监管 CLI 子进程、维护执行日志和上传产物。浏览器断开只会结束该设备的实时订阅。

~~~mermaid
flowchart LR
    web["桌面 / 手机浏览器"] -->|HTTPS| edge["私网反向代理"]
    edge -->|同源 Web、REST、SSE| control["控制服务"]
    control --> db["SQLite 与归档文件"]
    runner["Runner"] -->|本机套接字领取命令、回报结果| control
    runner --> journal["节点执行日志"]
    runner -->|stdio| cli["Codex app-server"]
    runner --> files["工作树与受限文件操作"]
    runner --> tests["受管测试执行器"]
    cli --> provider["用户选择的模型服务"]
~~~

控制服务启动时独占实例状态目录，执行结构版本检查，完成恢复后才对外报告就绪。Runner 启动时核对本地执行日志与控制服务记录，确认上次占用的写名额后才领取新的写任务。系统服务管理器分别监管两个常驻进程。浏览器不需要常驻。

## 2. 技术选型与调整条件

| 领域 | P1 决定 | 选择依据与重新评估条件 |
| --- | --- | --- |
| 后端与打包 | Go、标准库 HTTP，同一可执行文件提供控制服务和 Runner 两种启动角色。Go 嵌入预构建的 Web 静态资源 | 常驻服务共用发行包，主机不需要前端构建工具。执行主机另准备 Git、已认证的 CLI 和选定的隔离环境。独立升级需求出现后再拆发行包 |
| 客户端 | React、TypeScript、Vite，响应式 Web，同源提供页面与 API | 桌面和手机共用操作、状态与版本校验。P1 使用页面待办，依靠事件补读处理手机挂起 |
| 控制状态 | SQLite、WAL、本地持久磁盘。Go 使用 database/sql，驱动基线为 modernc.org/sqlite。落地时锁定驱动与其 SQLite 引擎版本 | 单实例写入便于把状态、授权决定、事件和待派命令放进同一事务。网络文件系统不作为 WAL 数据盘。需要多台控制服务同时写入时，重新评估 PostgreSQL。[SQLite WAL](https://sqlite.org/wal.html) · [驱动文档](https://pkg.go.dev/modernc.org/sqlite) |
| 大文件与日志 | 产物内容写入本地不可变归档，控制库保存清单、摘要和引用。Runner 在单独的本地 SQLite 文件中记录执行意图、可核实的启动身份、结果和待重发报告 | 控制库和节点日志分别提交，以命令和报告标识对账。差异大小与控制库体积解耦。未来跨节点共享归档时保留内容校验与版本引用 |
| 通信 | Web 命令和查询用 REST，状态推送用 SSE。Runner 主动经权限受限的 Unix 套接字拉取命令并上报 | 浏览器只需一个实例级订阅。变更有独立回执，可在断线后查询。P3 的跨机传输需另行设计节点身份与授权。[SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html) |
| 私网入口 | 选用 Caddy 作参考反向代理，也可接入所有者已有的等价入口。控制服务外部 HTTP 监听回环地址 | 代理只转发用户端路径，保持 SSE 流式传输。电脑与手机都要信任证书链。使用私有 CA 时由所有者将其根证书纳入两端信任。[Caddy HTTPS 文档](https://caddyserver.com/docs/automatic-https) |
| 仓库隔离 | 由可信 Runner 从固定提交创建独立 Git worktree。运行中固定基准，并保留实际交付的内容摘要 | 提交与工作树可追溯。文件和进程权限另外执行，避免借由共享 Git 元数据影响原仓库。[Git worktree](https://git-scm.com/docs/git-worktree) |

**平台基线。** 首个完整验证目标为 Linux x86_64，采用原生服务进程和 systemd。macOS arm64 是第二个候选目标，系统服务与进程约束分别验证。两种浏览器代表设备为桌面浏览器和 iPhone Safari。每项验证记录 OS、架构、文件系统、CLI、浏览器、驱动和产品构建版本。只有通过对应能力用例的组合才列为支持。

## 3. 模块归属与权限

| 模块 / 身份 | 可以读取与修改 | 负责的产品语义 |
| --- | --- | --- |
| Web 客户端 | 通过已配对设备会话读取允许展示的数据，提交带条件的命令 | 展示最后已确认状态，保留未确定回执的命令标识。断线补齐后再开放依赖当前版本的决定 |
| 控制服务 | 独占控制库、归档清单和设备会话。仅通过内部接口接收 Runner 数据 | 检查设备权限与版本，决定一次有效的受管授权或人工验收，维护队列、写名额和审计 |
| Runner | 读取已登记仓库、自己的工作目录和本地日志，可管理任务进程并向控制服务上传 | 负责启动与停止确认、实际进程身份、尝试编号、工作树隔离和可核实的运行结果 |
| Codex 适配器 | 与所监管的 CLI 交换结构化消息，在执行节点使用用户已有的模型登录 | 将 CLI 事件变成节点报告。分别声明原生续接、活跃任务中断、结构化答复与受控工具的可用性 |
| 文件操作与测试执行器 | 文件操作限定于本次工作树。测试执行器只取已授权动作与冻结输入，写独立临时目录和测试结果 | 校验路径、版本和批准的动作，实际启动与退出形成本地记录。工作树权限不应延伸到控制库、套接字或其他工作树 |

控制服务、Runner/工具代理、受限的 Agent 工具环境之间使用可强制的 OS 身份或等效隔离。只有 Runner 服务身份可以访问内部接口。模型认证仅对所需的 CLI 登录进程可用，测试进程和仓库内运行的工具拿不到模型凭据、设备 cookie 或服务端密钥。本地管理入口只向安装主机的管理者开放。

**Linux 验证方案。** 受管测试优先验证 rootless Podman。测试执行器从所有者预配置且按摘要固定的镜像启动一次性容器，只读挂载冻结输入，给输出与临时文件分配专用可写目录。默认关闭测试网络并设置时间、内存与进程数量限制。实例目录、用户主目录和运行时控制套接字均在挂载清单之外。该容器解决仓库测试代码的隔离，Agent 文件编辑和工具调用权限还须独立通过 G1。macOS 选择等价的执行环境后同样取证。[Podman 运行与挂载语义](https://docs.podman.io/en/latest/markdown/podman-run.1.html)

## 4. Codex 接入与首项受管测试

**协议入口。** 选取 Codex app-server 的本地 stdio 传输。适配器负责初始化连接、创建或续接 thread、开始 turn、响应受支持的工具与答复请求，并观察中断及最终状态。本轮仅核对了本机 CLI 0.171.0 的帮助文本和官方协议。这提供了候选接入点，CLI 与 NextBot 的端到端行为尚待实测。开发时使用所测版本的协议定义，并保存握手和能力记录。[Codex App Server 官方协议](https://developers.openai.com/codex/app-server)

| 收到的运行信息 | NextBot 的判断 |
| --- | --- |
| 创建 thread、接受 turn 或接到流式输出 | 仅记为已启动或有进展，保存原生引用 |
| CLI 表示 turn 完成 | Runner 仍须确认该尝试的写操作已结束、生成归档和校验证据。P1 进入待验收，P2 进入待复核 |
| 中断请求已送达 | 保留取消进行中的反馈。确认同一尝试的进程及受托子进程已停止后，才可释放写名额 |
| 进程或传输丢失 | 核对原进程与副作用。恢复原 thread 只恢复支持的对话上下文。已经启动的测试须另查节点日志 |

**权限可行性是第一项技术验证。** P1 的受管任务需要同时满足两件事。Agent 能通过限定的文件接口编辑本次工作树，预登记测试却只能由独立的测试执行器启动。候选方案让 Agent 通过窄接口请求读取、补丁和测试，关闭其通用命令入口和未经允许的外部工具。工具写入时校验工作树边界，保护 Git 管理区、服务配置和凭据。仅靠提示词、目录约定或一次 CLI 弹窗，均无法建立这一保证。

真实测试按以下顺序交付证据。

1. 所有者在 Agent 无写权限的位置登记测试定义、命令与参数、允许的工作区、超时和资源限制。
2. Runner 准备本次候选内容的不可变输入快照。命令定义版本、输入摘要、尝试、目标与执行范围共同绑定审批请求。手机展示这些内容。
3. 用户允许后，测试执行器核对命令和输入，记录启动意图，再在隔离环境中运行冻结的输入。测试脚本视作项目代码，使用独立写目录和有限权限。执行器优先采用预备好的依赖和工具链。拒绝、过期或输入变化时，本次授权不得启动测试。
4. 退出证据关联同一输入和产物。实际退出状态、输出引用、超时或中断都显示在验收页。启动边界发生崩溃且结果不明时，进入人工核对，保留所占名额。

受控配置的核验需覆盖可用工具、子进程、文件写入与批准/拒绝后的实际启动记录。若目标 CLI 无法在保留文件编辑的同时限制执行，标记该组合不兼容，继续做不依赖它的数据与界面工作。替代适配路径须重新经过同一组用例。P2 再为 Claude Code 验证独立只读复核，复核者读取冻结的产物和证据，不能直接运行仓库脚本。

## 5. 一次派发如何在断线后说清结果

1. 桌面发出创建或提交命令，控制服务在一个事务中保存命令回执、任务状态、事件和需要派发的工作。收到服务回执表示受理成功。
2. Runner 领取有身份和尝试范围的命令，先查自己的命令日志。只有当前尝试和写名额有效、先前未启动该动作时才能启动。控制服务的设备撤权不会把已批准且已启动的动作倒回。
3. 电脑关闭后，Runner 继续记录执行。服务端重连收取同一报告时只应用一次。迟到报告进入原尝试历史，仅当前尝试可推进任务。
4. 手机取同一读取时点的快照和事件高水位，从该处补读实时事件。两台设备同时决定时，服务端核验当前对象，保存先成立的决定。接收者遇到已处理的待办时看到实际结果。
5. 部分失败分别核对控制库中的意图、Runner 日志中的实际动作、归档中的证据。关键结论缺失时保留未决状态，让用户看见最后确认的事实。具体事务和恢复表见[持久化设计](03-data-recovery.md)。

## 6. 自托管交付与维护

以下是给首轮联调使用的可调初值。它们便于两端复现相同故障，正式发行值由真实设备测试确定。

| 参数 | 联调初值 | 到达阈值的行为 |
| --- | --- | --- |
| 节点心跳 / 失联判定 | 每 5 秒一次，连续 15 秒无有效心跳 | 显示最近联系时间并标记节点失联，仍保留未核实的写名额 |
| 命令领取租期 | 30 秒，可由有效连接续期 | 允许重新领取原命令并先对账，结果不明时保留人工核对 |
| 单次手机配对票据 | 签发后 5 分钟有效，最多兑换一次 | 尚未成功兑换的设备须向可信设备重新申请 |
| 分页快照 / SSE 补读 | 快照保留 2 分钟，同步事件以最近 24 小时为联调起点 | 过期后取得新快照与读取水位。任务历史、决定与归档有各自的保存规则 |

| 时机 | 维护动作与完成判断 |
| --- | --- |
| 首次安装 | 准备可持久写入的本地磁盘、可信的私网地址、已登录的目标 CLI 和一个已提交的仓库。启动控制服务与 Runner，在本机完成首次认领，给手机签发单次配对，再检查节点、能力和仓库可达性 |
| 日常诊断 | 分别显示控制服务、数据库、产物盘、Runner、CLI 登录与模型供应商状态。日志由任务、尝试、命令或报告标识关联。自由文本输出默认不随诊断导出。模型服务不可用时仍能读取历史、凭据状态和已有产物 |
| 备份 | 同一备份清单包含一致数据库快照和其引用的归档实体。校验对象数量和内容摘要。列明节点工作目录及模型登录等需单独维护的数据。P1 核验清单与重启后可读，P2 在干净实例做完整恢复演练。[SQLite Backup API](https://sqlite.org/backup.html) |
| 升级 | 暂停接收新的执行，先让在途写入完成或经用户确认取消，核对占用名额，做备份，再迁移结构。新版本确认数据库、写名额、节点和归档一致后恢复派单 |
| 回退 | 先停止派发并保全当前状态。仅在旧程序声明支持当前结构时直接回退程序。涉及不可逆结构变化时，从升级前备份恢复到隔离目录并核对升级期间实际执行记录，再选择可信实例接管 |

## 7. P1 评审决定

| 到达哪个关口 | 谁提供证据 | 影响的后续工作 |
| --- | --- | --- |
| 确认目标系统与 CLI 组合可强制约束文件编辑和测试 | Runner 负责人提供目标环境、能力清单、批准与拒绝后的真实记录，测试负责人复核 | 决定该组合能否作为 P1 执行环境。兼容性声明按逐项能力发布 |
| 证明一次决定只能产生一次有效控制记录 | 控制服务和存储负责人提供并发、重放及故障点的事务记录 | 完成后才把真实受管动作接入跨端审批 |
| 验证局域网双端使用和节点恢复 | Web、Runner 与测试负责人提供配对、掉线补读、取消和结果不明的证据 | 对齐全部 P1 用例后进入内部试用。P2 的发布门槛另行验收 |
