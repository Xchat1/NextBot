# NextBot 产品需求文档

**v0.1 评审稿 · 2026-11-27 · 首个可用版本以 P2 为发布线**

本稿用于确定产品范围、取舍与发布条件。文中的能力和指标均为规划目标。界面流程见[产品体验与操作说明](02-product-guide.md)，状态、权限和验收用例见[功能规格与验收](03-functional-spec.md)。

## 1. 产品要解决的问题

一个维护者在自己的 Mac 或 Linux 主机上用编码 Agent 修复问题。人离开电脑后，执行仍然需要继续。第二个 Agent 复核时，需要知道最初的要求、实际改了什么、哪些测试真的跑过。手机上出现“请确认”时，人需要知道这次确认针对哪一个版本、确认后会发生什么。机器掉线时，人还需要判断该等待、续接还是重试。

**产品目标**是让一个人用自己的设备和 Agent 账号，完成从派单、执行、独立复核到跨端验收的一项工作。NextBot 负责协调和保留证据。模型提供推理，执行节点持有进程和工作文件，用户保有接受或退回产物的决定权。

**首发假设**是个人开发者每周都有重复发生、能描述验收条件的仓库任务，一台常在线主机足以覆盖早期使用。响应式 Web、Codex CLI 和 Claude Code 是建议的首发组合。目标用户、客户端形态和适配器顺序都可在产品评审时调整。

## 2. 用户、场景与价值验证

| 使用者与时机 | 想完成的事 | 产品必须给出的答案 |
|---|---|---|
| 任务发起人，在桌前 | 选择仓库，说明目标、限制与验收条件后离开 | 任务已交给哪台机器、哪个 Agent，现在能否安全关闭页面 |
| 产物验收人，在手机上 | 利用间隙判断某项工作能否接受 | 哪一版产物、改了什么、复核结论、证据缺口，以及接受后的效果 |
| 实例维护者，故障后 | 找回任务记录，判断正在运行的工作还能否续接 | 最后确认的步骤、进程与会话是否仍在、恢复需要哪些数据 |

首版由同一个人承担这三种职责，电脑和手机属于同一所有者。多用户、组织角色与跨人审批在后续版本单独设计。

**首个实用场景**是修复一个有明确复现条件的导出错误。发起人要求保留已有导出格式，并提供失败输入的回归测试。执行 Agent 交付变更和测试记录，复核 Agent 核对需求、差异和证据。若漏测空数据，退回原因和目标版本会带入下一次执行。手机只在需要授权、补充信息、处理异常或验收时占用用户注意力。

**首要产品指标**是“可独立验收任务占比”。每项实际进入人工验收的任务，按它第一次进入待验收的版本计一次。试用者打开手机待办后，仅凭任务页信息便可说明版本、引用证据并做出接受或退回决定，即计入分子。复核阶段已拦截的版本另测。上线后同时观察从建单到首次交付的耗时、每单人工干预次数与退回原因。

## 3. 七个参照项目如何影响取舍

| 参照 | 观察与决定 |
|---|---|
| Orca | 其实验性编排区分任务与每次派发。NextBot 给每次执行独立身份，用它归属结果和处理迟到回执。[官方编排文档](https://orca.dev/docs/cli/orchestration) |
| Paseo | 常驻进程配合客户端事件补读。NextBot 让设备断开与任务运行有各自的生命周期。[连接方式](https://paseo.sh/docs/connectivity) · [事件恢复](https://paseo.sh/docs/sdk/events) |
| TaroBird | 同机协作可以绑定不同 Bot 的会话，跨机传任务则需要有方向的授权。NextBot 先做单机交接，把跨机调度留给 P3。[官方项目说明](https://github.com/cloveric/tarobird#readme) |
| Herdr | 后台进程仍在、原生会话可续接、仅保留历史是三种不同的恢复结果。NextBot 要向用户呈现真实可用的恢复选项。[会话恢复](https://herdr.dev/tui/docs/session-state/) |
| Paradev | 独立工作树让变更可比较、选择和评审。NextBot 将差异版本和测试记录放在验收页。[官方并行评审流程](https://docs.paradev.com/recipes/race-agents) |
| T3 Code | 多端控制和持久工作流已有对照，其中工作流在主分支中标为默认关闭的 Labs 功能。NextBot 以完成同一任务的操作成本与故障恢复体验作比较。[官方项目说明](https://github.com/pingdotgg/t3code#what-you-get) · [工作流说明](https://github.com/pingdotgg/t3code/blob/main/skills/t3-workflows/SKILL.md) |
| OpenBot | 工具调用经过策略裁决，动作与决定可以追溯。NextBot 对其能约束的动作展示权限、目标和结果，保留将来接入通用 Bot 的空间。[官方架构](https://github.com/CopilotKit/OpenBot/blob/main/docs/architecture.md) |

## 4. 发布范围与优先级

P0 是文档和场景评审，P1 是内部可试用的单 Agent 路径，P2 是第一个面向个人自托管用户的完整版本。P1 的单 Agent 路径可直达人工验收，P2 的标准交付要求当前产物通过独立复核。

交付顺序从 Mac 桌面应用开始。用户先在一台 Mac 上完成登记本机仓库、派单、查看差异和验收。单机流程通过后，再验证手机接手与跨端同步。云端部署排在手机体验之后。

| 能力 | P1 内部试用 | P2 首发增量 |
|---|---|---|
| F01 自托管与数据恢复 | 一台主机部署、私网 HTTPS 访问、持久存储 | 用备份在干净实例恢复任务、决定与关键产物，验证完整性 |
| F02 身份与设备 | 初始化所有者、桌面登录、手机配对及撤销 | 验证双端竞争和移除丢失设备后的访问边界 |
| F03 节点与适配器 | 单节点、Codex CLI、探测可用能力与登录状态 | 加入 Claude Code，按执行与只读复核能力分配角色 |
| F04 项目与工作区 | 选择允许访问的 Git 仓库，记录基准版本，在独立工作树执行 | 每轮交付可追溯到上轮产物，复核只读 |
| F05 任务与调度 | 草稿、提交、排队、取消和单节点写入并发限制 | 固定“执行 → 复核 → 人工验收”流程，可退回返工 |
| F06 执行与恢复 | 持久化执行尝试，处理客户端断开、进程退出和节点失联 | 对两种接入分别验证续接能力，拒绝旧尝试覆盖新结果 |
| F07 交接与复核 | 记录交付目标和执行结果，为后续复核保留输入 | 独立会话、强制只读、带证据的结论和有上限的返工 |
| F08 产物与验收 | 查看差异与测试记录，人工接受指定版本 | 校验复核结论与产物版本一致，保留历次版本及决定 |
| F09 受管动作授权 | 对一次预登记的测试命令展示工作区、版本和参数，允许本次或拒绝，过期即失效 | 双端竞态、断线、不确定是否执行的情况均有可诊断结果 |
| F10 跨端事件与待办 | 响应式 Web、同一任务时间线、断线补读 | 按需决策组织手机待办，相同事项两端同步消除 |
| F11 审计与诊断 | 查看关键事件、错误原因、状态与取消结果 | 能串起任务、执行、授权、产物、复核与最终决定，支持脱敏诊断 |

**延期范围**包括原生移动 App、公网穿透中继、多人团队和租户管理、跨节点自动选机、自由画布编排、模型市场、办公工具连接器。自动提交、合并、推送和部署也在首发范围之外。用户接受产物后，差异和工作区仍可由其自行处理。

## 5. 产品架构与责任

| 边界 | 拥有的数据与职责 | 设计约束 |
|---|---|---|
| 控制服务 | 任务、当前尝试、事件顺序、决定、产物索引、设备权限 | 所有客户端以服务确认的状态为准。处理重复请求时返回已有决定 |
| 执行节点 Runner | 本地 CLI、模型登录凭据、进程、工作树、产物采集 | 通过明确的适配器回执更新执行结果。节点失联时保留最后确认状态 |
| Agent 适配器 | 将启动、输出、受管工具请求、退出与原生续接能力映射到公共接口 | 逐项声明能力。能强制只读的适配器和环境才有资格承担复核 |
| Web 客户端 | 展示任务、待办、差异、审批对象和最新处理结果 | 设备可断开，关闭页面即离开观察界面。重连依据服务端记录补齐 |

~~~mermaid
flowchart LR
    desktop["电脑浏览器"] -->|私网 HTTPS| control["自托管控制服务"]
    phone["手机浏览器"] -->|私网 HTTPS| control
    control -->|派发任务与已授权动作| runner["执行节点 Runner"]
    runner -->|状态、产物与证据| control
    runner --> executor["执行 Agent"]
    runner --> reviewer["独立只读复核 Agent"]
    control --> archive["任务记录与产物归档"]
~~~

P1 和 P2 的控制服务与 Runner 可以同机运行。自托管的验收边界是无需注册 NextBot 厂商账号，也能在私网部署、配对、保存与恢复自身记录。用户所选模型服务仍按其自身方式认证和联网。模型密钥留在执行节点。任务摘要、日志和产物要说明保存位置与导出范围，避免把供应商登录材料混入备份或诊断包。

**任务与会话分别保存。** 任务说明用户想得到什么，一次执行尝试说明谁在何处做过什么，产物版本说明提交评审的内容。会话是某个 Agent 的上下文。适配器无法恢复原会话时，仍可凭任务目标、产物与测试证据发起新的尝试，并保留两次尝试的关系。

## 6. 首发质量目标与验证方式

下表是建议的发版门槛，尚无实测数据。耗时目标在同一私网、预装并已登录 CLI 的环境下测量。模型推理时间单列。试用指标由所有者本地记录或由试用者主动提供。

| 验证项 | 样本与方法 | P2 通过条件 |
|---|---|---|
| 自托管首次使用 | 3 位目标用户分别从干净的支持环境开始，已有仓库和模型账户 | 至少 2 位在 20 分钟内完成部署、配对和首次派单，无需开发者代操作。发布说明列明实际验证过的平台 |
| 手机独立验收 | 3 位试用者合计处理 10 项进入人工验收的真实任务。加入已通过复核、用户读到样本后仍有理由退回的任务 | 至少 8 项可在手机上说明版本、引用证据并作出决定。接受和有依据的退回均计入 |
| 独立复核拦截 | 另准备两份缺少必需证据的产物，一份缺回归测试记录，一份只有无对应版本的旧记录 | 两份均被独立复核退回，给出具体缺项，手机上均不能接受相应版本 |
| 决定的唯一性 | 同一授权或验收在两端同时提交，覆盖重复点击、相反决定、断网重发，共 30 组 | 每组仅一个有效决定，另一端能看到已生效的结论 |
| 离线与故障恢复 | 客户端掉线、控制服务重启、节点失联、进程丢失、动作结果未知各演练一次 | 可找回已确认决定与产物引用。界面准确给出恢复选项，并阻止自动重做结果未知的外部动作 |
| 产物一致性与权限 | 旧产物过期、复核中返还旧结果、越界写入、已撤销设备重连等用例 | 旧结论不能验收新版，越界写入被执行环境阻止，撤权后不能继续读取或提交决定 |
| 数据可携带性 | 将一份已完成和一份中断的任务备份恢复到干净实例 | 可打开产物和证据、追溯有效决定，并准确标识需重新连接的工作区或会话 |

上线前用自有真实任务分别演练顺利交付、退回补测、执行期间离线三条路径。保留脱敏的操作记录和失败原因。只要出现错误接受版本、重复执行受管动作、复核越权写入这三类问题之一，即阻断发布。

## 7. 里程碑和评审决定

| 阶段 | 交付及退出条件 |
|---|---|
| P0 文档评审 | 维护者走读三份文档，确认首批用户、默认 Agent 组合、接受产物的含义及哪些数据要备份。可用本文的导出修复场景桌面推演 |
| P1 单机跨端 | 一位所有者可以由桌面派单、关页、换手机处理待办，并能区分主机故障和浏览器断开 |
| P2 双 Agent 首发 | 同一节点完成执行、只读复核、返工与手机验收，并完成上表的试用和故障演练 |
| P3 扩展验证 | 用第二台受权机器承接子任务，再用“资料整理 → 独立核验 → 报告审批”验证非代码产物。根据实际需要再排团队权限和连接器 |

**值得在进入开发前拍板的三项决定**是首发支持的操作系统与架构清单、两种 CLI 所需验证的版本、以及个人用户可以接受的安装与配对成本。当前建议先在一台日常使用的 Mac 和一台 Linux 主机各做一次兼容性验证，再公布支持矩阵。P2 必须在至少一个公布支持的环境中跑通“Codex 执行、Claude Code 强制只读复核”。反向组合在独立通过同样的权限和恢复验证后才向用户开放。

**主要风险与处理。** CLI 升级可能改变恢复或审批能力，发布时记录验证版本并显式降级。模型给出“测试已通过”的文字可能缺少执行证据，交付页须区分测试记录与 Agent 自述。工作树能隔离文件改动，凭据、进程与网络访问仍由执行环境分别约束。自托管备份必须覆盖实际产物内容，并显式标记只能重新连接的外部仓库或原生会话。

## 8. 从个人工具扩展为通用编排底座

后续演进沿用首发的任务、执行尝试、产物与决定记录。下表是候选方向，按前置条件进入评审，不承诺交付日期。

| 后续方向 | 第一个有价值的用法 | 进入下一阶段的证据 |
|---|---|---|
| 多节点委派 | Mac 上发起任务，指定 Linux 节点完成兼容性验证，将报告归入原任务 | 接收节点能拒绝越权委派。断开再连可追溯实际执行者、输入版本、输出和回执 |
| 并行任务与依赖 | 对同一基准并行做兼容性检查与文档复核，两份结果都到齐后才进入验收 | 阻塞原因能定位到具体子任务。一个分支失败只需重试该分支。取消能传递到仍在运行的子任务 |
| 非代码产物与工具接入 | 资料收集 Agent 提交来源，复核 Agent 对引用逐条核对，手机验收最终报告 | 报告、引用和核验结论可以按版本交接。引入新工具时，有明确的身份、授权与数据保存范围 |
| 小团队共享 | 两位同事共用一台受管节点，按项目分工发起、执行与验收 | 项目可见性、操作者身份、可批准动作和设备撤权均可验证，并能查清某次决定由谁作出 |

优先顺序取决于首批用户实际遇到的障碍。若单机任务依然频繁卡在证据缺失或恢复，先修订 P2 的交付体验。若问题集中在特定操作系统或多人排队，再推进多节点。这样每项扩展都有一个可观察的理由和可复验的退出条件。
